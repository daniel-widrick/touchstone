# Auditing and reviewing

How to judge a UI against the rules without changing it: a running product
(an audit), or a change from its diff (a review). Both end in a list of
verdicts with evidence. Make no edits while doing either.

## Verdicts

Every applicable rule gets one of these, and the report keeps them apart:

- `pass` or `fail`, with the evidence quoted first: a line of code with its
  location, a measured value, or what you did and what happened.
- `cannot tell: no evidence`. Nothing showed either way. This needs a walk
  or a measurement, not a person's opinion.
- `cannot tell: split`. A judgment rule was decided twice and the two
  verdicts disagreed. This is worth a person's look.
- `not run`. The rule needs a running page or a walk and none was
  available, as in a code review. This is not a finding about the product.

No evidence is never `pass`. Take severity from the rule record; do not
re-rate it.

## Walking a UI safely

Walking tasks through their failure, slow and empty states finds the
problems that matter most, and it must not touch real data. Fake the network
in the browser instead of breaking the server:

- `scripts/fake-network.js` wraps the page's own `fetch`, `XMLHttpRequest`,
  `sendBeacon` and native form posts. Set `window.__uxNet` first, then run
  the file in the page. `{ blockWrites: true }` makes every POST, PUT, PATCH
  and DELETE fail without leaving the browser. `fail`, `status`, `delayMs`
  and `empty` force failures, slow responses and empty lists for URLs
  matching a pattern. What the page tried to send is recorded in
  `window.__uxNet.log`.
- To affect requests made while the page loads, the script must run before
  the page's own: `page.addInitScript` in Playwright, or
  `Page.addScriptToEvaluateOnNewDocument` in Chrome DevTools. `run.py` does
  this with `--block-writes`, `--fail`, `--status`, `--delay` and `--empty`,
  and with `--block-writes` it also fails non-GET page navigations in the
  browser itself, which catches form posts the in-page script cannot see.
- The in-page script cannot see a write made by a browser extension, a
  service worker, or a form posted into another window. On a server-rendered
  product whose data matters, prefer `run.py` or a Playwright route that
  aborts non-GET requests, and check the log before trusting that nothing
  was written.
- Turn on write-blocking before any walk of a product whose data matters, and
  report what the log shows the page tried to write.

When several auditors walk the same product at once, each needs its own
browser (its own Playwright context or profile), with write-blocking on.
Never share one browser between agents: they move each other's focus,
scroll and open dialogs, and their findings stop meaning anything. `run.py`
starts a fresh browser profile on every run, so its runs can go in parallel.

### Signed-in screens

- Save a signed-in session once and reuse it: sign in by hand in Playwright
  and save its storage state (`context.storageState({ path })`), then pass
  that file to each auditor's browser, or to `run.py --storage-state FILE`.
  `run.py` also takes `--cookie NAME=VALUE` and `--header 'NAME: VALUE'`.
- For two-factor sign-in, use a test account. A test account whose one-time
  codes can be generated by a script is fine; keep its secret in the
  environment or a secret store, never in the repository, the skill or a
  report.
- Sessions expire. The checker warns when it was redirected away from the
  address it was given, or when the page looks like a sign-in page. Treat a
  run with that warning as measuring the wrong page, and sign in again.

## When auditing a running UI

A single pass finds a minority of problems, and coverage rises when
independent passes are merged. If you can start subagents, give each relevant
domain to a separate one (the `touchstone:ux-auditor` agent where it is
installed, or any fresh agent told to follow this file for one domain file),
each with its own browser and write-blocking on, then merge their reports as
below. Otherwise take the domains one at a time yourself.

Set a time budget per domain before starting, and give it to each auditor.
Without one from the person asking, use about 15 minutes per domain. When the
budget runs out, stop and report what you have; each rule not yet judged is
`cannot tell: no evidence` with "out of time" as the reason.

For each domain:

1. **Scope.** State the screens and the user tasks being judged.
2. **Applicability.** For each rule in the file, decide from `Applies when`
   whether it applies. Record not-applicable rules by id; do not skip
   silently.
3. **Measure.** Run the checker. Attach its results to the rule ids it names.
   Discard any run that warns it measured a loading state, a redirect or a
   sign-in page, and measure again.
4. **Verdict per rule.** As in "Verdicts" above. For rules whose evidence is
   judgment, decide twice, the second time starting from the last rule; a
   disagreement is `cannot tell: split`.
5. **Walk.** For each task, go through it in the running UI. At every step
   ask: is the control I need visible, would I recognize it as the right one,
   and did the screen show that my action worked? Then walk it again with
   its requests failing, slow and empty, using the fake network with writes
   blocked. Record failures against the matching rule.
6. **Open pass.** Separately, note anything that hurt the task and matched no
   rule. Mark these as lower confidence. Do not aim for a number of findings.

## Reviewing a change

A pull request or a diff, judged from the code, with or without a preview.

1. **Scope.** List the screens the change touches, and only those. Unchanged
   screens are out of scope even if they have problems.
2. **Domains.** Load the domain files those screens need (at most four at a
   time).
3. **What code can settle.** The end of `references/brief.md` sorts the
   rules by what a code review can do with them: settle from the code alone;
   settle from the markup when the diff shows it plainly; trace through the
   code when the handlers are plain to follow (what happens on submit, on
   failure, on leaving); or not at all without a running page. Judge what
   the code lets you judge, with the line quoted. Mark the rest `not run`,
   not `cannot tell`.
4. **If a preview is available,** run the checker and walk the changed tasks
   as in an audit; those rules then get ordinary verdicts.
5. **Report** as below. List `not run` rules by id on one line, so a reader
   can see what a later walk would need to cover.

The `touchstone:ux-auditor` agent does this when given source or a diff
without a running UI.

## After fixes: judge them again

A fix that works can still break a rule. After fixing, re-run the rules of
every domain the change touched on the changed screens, including the
checker and the walk where you have a running page. Judge the fix itself,
not only that the problem went away: a "Back to the form, with your entries"
link that works still has to meet the rules for its wording, its place and
what it keeps.

## Merging reports

Parallel auditors find the same defect, often under different rules. Merge
before reporting:

- Group findings by defect: the same element and the same cause, or one root
  cause showing on several screens (typed input lost on every step of a
  flow is one defect).
- Each defect is one entry: the highest severity among its rules, every rule
  id it fails, every location, and the evidence from each auditor.
- Count defects, not rule failures. Give both numbers in the counts.
- When auditors disagree on a verdict for the same rule and screen, report
  the evidence from each and mark it `cannot tell: split`.

## Report

In this order:

1. Failures, by defect, most severe first: the rule ids, the rule in a few
   words, locations, evidence, and the smallest fix.
2. Failures in third-party markup, listed separately by library, with what
   the product can do about each (see "Third-party markup" in the skill).
3. `cannot tell: split`, with both verdicts' evidence.
4. `cannot tell: no evidence`, with what would be needed to decide.
5. `not run`, by id on one line.
6. Counts: rules applicable, passed, failed, each kind of cannot tell, not
   run, not applicable; and the number of distinct defects.
7. Open-pass notes, labeled as such.

Give no overall score and no summary judgment of quality.
