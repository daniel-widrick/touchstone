## 1 Data Entry

### 1.0 General

- 1.0/1 | Data Entered Only Once | Anything a user has already supplied must be reused by the system wherever it is needed again, in the same task or a later one, instead of being asked for twice. | tasks | interaction |
- 1.0/3 | Feedback During Data Entry | Every keystroke and input action shows a visible result as it happens. | feedback | interaction | exception: passwords and other secret entries
- 1.0/6 | Defined Display Areas for Data Entry | Places where the user can enter data must be visibly marked out as entry fields. | forms | script | exception: free-form text of unrestricted length
- 1.0/7 | Consistent Method for Data Change | Any earlier entry, including a prefilled default, can be changed using the same ordinary editing actions everywhere. | forms | interaction |
- 1.0/8 | User-Paced Data Entry | The user sets the pace of entry; the system does not impose time limits or advance on its own schedule. | tasks | interaction | reword: no forced timeouts on forms
- 1.0/9 | Explicit ENTER Action | Entered data is processed only when the user deliberately submits it, never as a by-product of another action. | actions | interaction | exception: routine repetitive entry may chain to the next item
- 1.0/10 | ENTER Key Labeling | The control that submits data carries a label that says what it does. | actions | script | reword: applies to the submit button, not a keyboard key
- 1.0/11 | Explicit CANCEL Action | Discarding an entry requires a deliberate cancel action and never happens as a side effect of something else. | actions | interaction |
- 1.0/12 | Feedback for Completion of Data Entry | After submission the system always reports either success or an error. | feedback | interaction | exception: repetitive entry may simply show the cleared form
- 1.0/16 | Partitioning Long Data Items | Long codes and numbers are broken into short groups for both entry and display. | forms | script |
- 1.0/24 | Prompting Data Entry | Tell the user what format and what values an entry accepts. | forms | script | exception: skilled users on slow output
- 1.0/27 | Upper and Lower Case Equivalent | Coded entries are accepted regardless of letter case. | forms | interaction |

### 1.1 Position Designation

- 1.1/13 | Large Pointing Area for Option Selection | The clickable or tappable region of an option covers at least its whole label plus a margin around it. | access | script | reword: hit target includes label and padding
- 1.1/21 | Consistent Cursor Placement | When an entry screen opens, input focus starts in a consistent and useful place. | access | interaction | reword: initial focus rather than cursor
- 1.1/24 | Data Entry Independent of Cursor Placement | Submitting a form sends every field, no matter which field currently has focus. | forms | interaction |

### 1.3 Text

- 1.3/34 | User Confirmation of Editing Changes | When the user finishes editing, let them choose whether to apply the changes to the original or do something else, such as discard. | feedback | interaction |

### 1.4 Data Forms

- 1.4/1 | Combined Entry of Related Data | Related fields are submitted together with one action at the end, not one submission per field. | forms | interaction |
- 1.4/2 | Flexible Interrupt | Before the final submit, the user can review the whole form, cancel it, or go back and change any item. | forms | interaction |
- 1.4/3 | Minimal Use of Delimiters | Do not make users type separators such as hyphens or currency signs inside entries. | forms | interaction |
- 1.4/5 | Data Field Labels | Every entry field has a visible label indicating what goes in it. | forms | script |
- 1.4/6 | Consistent Labeling | The same kind of data gets the same label wherever it is requested. | copy | judgement |
- 1.4/8 | Labels Close to Data Fields | A label sits near enough to its field to be read as belonging to it, with a small gap between them. | forms | script |
- 1.4/11 | Prompting Field Length | The field's appearance signals any fixed or maximum length for the entry. | forms | script |
- 1.4/12 | Marking Required and Optional Data Fields | Required and optional fields are told apart clearly and in the same way throughout. | forms | script |
- 1.4/15 | Explicit Tabbing to Data Fields | Focus moves to the next field only when the user moves it; the form does not jump ahead automatically. | access | interaction | reword: no auto-advance on filled fields
- 1.4/19 | Informative Labels | Labels use descriptive words or established terms, never arbitrary codes. | copy | judgement |
- 1.4/20 | Data Format Cueing in Labels | Where it helps, the label or a hint next to it shows the expected format of the entry. | forms | script |
- 1.4/21 | Labeling Units of Measurement | When a field always uses one unit, show the unit with the field so the user does not type it. | forms | script |
- 1.4/24 | Form Compatible for Data Entry and Display | The entry form and the read-only view of the same record use the same labels in the same order. | forms | script |
- 1.4/27 | Data Items in Logical Order | Absent a source document to follow, order fields in the sequence users naturally think of them. | forms | judgement | exception: match the source document when transcribing
- 1.4/28 | Automatic Cursor Placement | When a form appears, focus is placed in the first entry field. | access | interaction | exception: after an error, focus the first field in error

### 1.5 Tables

- 1.5/9 | Aiding Entry of Duplicative Data | Where table entries often repeat, provide an easy way to copy an earlier value. | forms | interaction |

### 1.7 Data Validation

- 1.7/1 | Automatic Data Validation | The software checks every entry whose presence, format or content matters for later processing. | forms | interaction |
- 1.7/2 | Accepting Correct Entries | Validation must never reject an entry that is actually valid. | forms | interaction |
- 1.7/3 | Non-Disruptive Error Messages | A suspected error is reported once the user has finished the entry, not in the middle of it. | feedback | interaction |
- 1.7/5 | Reminder of Deferred Entry | If required items were left for later and the user tries to proceed, point out what is missing and let them fill it in on the spot. | forms | interaction |

### 1.8 Other Data Processing

- 1.8/1 | Default Values | Where a likely value can be predicted, offer it as a default. | tasks | judgement |
- 1.8/4 | Display of Default Values | Defaults are shown in their fields when the form opens, not applied invisibly. | forms | script |
- 1.8/7 | Automatic Generation of Routine Data | Routine data the system can look up from its own records is filled in automatically. | tasks | judgement | exception: re-entry imposed for security
- 1.8/8 | Automatic Computation of Derived Data | Never ask the user to calculate and type a value the system can derive from data it already has. | forms | judgement |
- 1.8/9 | User Review of Prior Entries | When earlier entries bear on a later step, show them there for review instead of asking again. | tasks | interaction |
- 1.8/10 | Automatic Entry of Redundant Data | Items logically implied by other entries are retrieved and filled in by the system. | forms | interaction | exception: disambiguation, training, security

## 2 Data Display

### 2.0 General

- 2.0/1 | Necessary Data Displayed | Everything the user needs to complete the current step is available on screen. | data | judgement |
- 2.0/2 | Only Necessary Data Displayed | Show only what the current step needs and leave out everything else. | data | judgement |
- 2.0/3 | Data Displayed in Usable Form | Present values ready to use, so users never have to convert or decode them. | data | judgement |
- 2.0/11 | Context for Displayed Data | Each screen repeats enough earlier information that users need not remember it from a previous screen. | tasks | judgement |
- 2.0/12 | Familiar Wording | Use the users' own task vocabulary, not the vocabulary of designers and programmers. | copy | judgement |
- 2.0/13 | Consistent Wording | Pick a term for each thing and use that term every time. | copy | judgement |
- 2.0/16 | Minimal Use of Abbreviation | Prefer whole words to abbreviations. | copy | judgement | exception: much shorter, space is tight, and users know them

### 2.1 Text

- 2.1/6 | Conventional Use of Mixed Case | Running text is set in normal mixed case, not all capitals. | copy | script | exception: a short label or title meant to attract attention
- 2.1/11 | Clarity of Wording | On-screen text, guidance especially, is worded simply and clearly. | copy | judgement |
- 2.1/17 | Active Voice | Write sentences in the active voice. | copy | judgement |
- 2.1/19 | Lists for Related Items | A series of related items is shown as a list, not buried in a paragraph. | data | judgement |
- 2.1/23 | Logical List Ordering | Lists follow an evident ordering principle, falling back to alphabetical when none applies. | data | judgement |

### 2.2 Data Forms

- 2.2/3 | Data Field Labeling | Every displayed data field has a label. | data | script |
- 2.2/5 | Consistent Wording of Labels | The same data item carries the same label on every screen where it appears. | copy | judgement |
- 2.2/7 | Consistent Label Location | Labels are placed consistently, either above or to the left of their fields. | forms | script |
- 2.2/10 | Labeling Units of Measurement | Displayed quantities show their unit, in the label or with the value. | data | script |
- 2.2/11 | Consistent Format Across Displays | Corresponding fields appear in the same order and arrangement from one screen to the next. | data | judgement |

### 2.3 Tables

- 2.3/1 | Tables for Data Comparison | Use a table when users must compare ordered sets of data in detail. | data | judgement |
- 2.3/4 | Tables Referenced by First Column | Put the item users look up by in the leftmost column, the most relevant data next to it, and less important data further right. | data | judgement |
- 2.3/6 | Row and Column Labels | Table rows and columns are labelled to the same standard as form fields. | data | script |
- 2.3/11 | Labeling Units of Measurement | Units in a table are shown consistently, in the column heading or after the first entry. | data | script |
- 2.3/14 | Row Scanning Cues | Dense tables with many rows get a regular visual break or similar cue to help the eye follow a row. | data | script | reword: zebra striping, row hover or group gaps
- 2.3/15 | Justification of Alphabetic Data | Text columns are left-aligned. | data | script | exception: indentation for hierarchy
- 2.3/16 | Justification of Numeric Data | Numeric columns are aligned on the decimal point, or right-aligned when there is none. | data | script |

### 2.4 Graphics

- 2.4.1/3 | Labeling Axes | Each chart axis is labelled with what it measures and its unit. | data | script |

### 2.5 Format

- 2.5/1 | Consistent Format | Recurring screen elements occupy the same location on every screen. | data | judgement | exception: deliberate change to mark a different task
- 2.5/3 | Spacing to Structure Displays | Use blank space to show the structure of a screen. | data | judgement |
- 2.5/10 | Display Title at Top | Every screen starts with a title that briefly states its content or purpose, set apart from the body. | navigation | script |
- 2.5/12 | Logical Data Organization | Items on a screen are grouped according to an evident logical principle derived from the task. | data | judgement |
- 2.5/16 | Data Grouped by Importance | Items that matter most or need an immediate response go at the top. | data | judgement |

### 2.6 Coding

- 2.6/1 | Highlighting Critical Data | Items that need attention, especially rare ones, are given distinctive emphasis. | data | judgement |
- 2.6/2 | Removing Highlighting | Emphasis is removed once it no longer means anything. | states | interaction |
- 2.6/7 | Consistent Coding Across Displays | A symbol, colour or other code means the same thing on every screen. | data | judgement |
- 2.6/28 | Conservative Use of Color | Use few colours for coding and reserve them for the categories that matter. | data | judgement |
- 2.6/30 | Redundant Color Coding | Never convey a distinction by colour alone; pair it with a symbol, text or other feature. | access | script |

### 2.7 Display Control

- 2.7.2/1 | Integrated Display | Everything relevant to the current transaction is on one screen, not split across several. | data | judgement |
- 2.7.2/4 | Labels for Multipage Tables | Column headings and row labels stay visible in every part of a table too large for one view. | data | script | reword: sticky headers, or headers repeated per page
- 2.7.2/5 | Annotating Display of Continued Data | Make clear when a list or table continues beyond what is shown and when its end has been reached. | states | script | exception: short lists whose end is obvious
- 2.7.3/2 | Highlighting Changed Data | Values that changed in an automatic refresh are briefly highlighted. | feedback | interaction |
- 2.7.4/2 | Labeling Display Suppression | When some data has been hidden from a view, say so on the view. | states | script | reword: show an active-filter or hidden-columns indicator
- 2.7.4/4 | Resuming Display of Suppressed Data | Provide a quick way to bring a filtered or reduced view back to its complete form. | data | interaction | reword: a clear-filters control

## 3 Sequence Control

### 3.0 General

- 3.0/2 | Minimal User Actions | A transaction takes the fewest and simplest actions consistent with what users can manage. | tasks | judgement | exception: destructive actions deliberately take extra steps
- 3.0/5 | Control by Explicit User Action | The system starts processing or moves to another step only when the user explicitly asks. | actions | interaction | exception: emergency alerts; chained repetitive entry
- 3.0/6 | Consistent User Actions | Similar goals are achieved by similar actions with similar results throughout the interface. | actions | judgement |
- 3.0/9 | Displayed Context | If what an action does depends on an earlier choice, that choice stays visible. | states | judgement |
- 3.0/14 | Feedback for Control Entries | Every user action gets an immediate, visible reaction. | feedback | interaction |
- 3.0/15 | Indicating Completion of Processing | When processing takes a while, announce clearly when it has finished and what came of it. | feedback | interaction |
- 3.0/20 | Indicating Control Lockout | If input cannot be accepted while earlier work is processed, show that the interface is busy. | states | interaction |
- 3.0/21 | Interrupt to End Control Lockout | During a long blocking operation the user still has a way to abort it. | actions | interaction | reword: a cancel control that stays live during loading

### 3.1 Dialogue Type

- 3.1.1/3 | Recapitulating Prior Answers | In a step-by-step sequence of related questions, earlier answers are shown where they help with the current one. | tasks | script |
- 3.1.3/9 | Feedback for Menu Selection | If choosing an option has no naturally visible effect, the system acknowledges the choice in some other way. | feedback | interaction |
- 3.1.3/11 | Menu Options Worded as Commands | Options read as commands the user gives, not as questions put to the user. | copy | judgement |
- 3.1.3/18 | Menu Options Dependent on Context | A menu shows only the options actually available to this user in the current context. | actions | judgement | exception: clearly marked not-yet-implemented options
- 3.1.3/21 | Logical Ordering of Menu Options | Options are listed in a logical order, or by expected frequency of use when no logic applies. | navigation | judgement |
- 3.1.3/22 | Logical Grouping of Menu Options | Related options are visibly grouped, not presented as one undifferentiated run. | navigation | judgement |
- 3.1.3/24 | Labeling Grouped Options | Each group of options has a descriptive heading that looks different from the options themselves. | navigation | script |
- 3.1.3/26 | General Menu | There is a top-level set of basic options that the user can always return to as a starting point. | navigation | interaction | reword: a home or main navigation
- 3.1.3/30 | Indicating Current Position in Menu Structure | The user's current location in a navigation hierarchy is shown. | navigation | script | reword: active nav item, breadcrumb
- 3.1.3/31 | Control Options Distinct from Menu Branching | Options that perform an action look different from options that only lead to further choices. | actions | script |
- 3.1.8/4 | Supplementary Verbal Labels | An icon that stands for an action is accompanied by a text label. | actions | script |

### 3.2 Transaction Selection

- 3.2/10 | Only Available Options Offered | Do not offer controls that cannot be used in the current transaction. | actions | interaction |
- 3.2/12 | Consistent CONTINUE Option | When only one next step makes sense, a consistently presented continue control leads to it. | tasks | script | exception: data entry still needs an explicit submit

### 3.3 Interrupt

- 3.3/1 | User Interruption of Transactions | Users can interrupt or abandon a transaction in progress. | actions | interaction |
- 3.3/3 | CANCEL Option | Cancel wipes the changes just made and restores the screen to its previous state. | feedback | interaction |
- 3.3/4 | BACKUP Option | A back action returns to the previous step without destroying anything. | navigation | interaction |
- 3.3/5 | REVIEW Option | The user can go back to the start of a multi-step sequence to check and change entries without losing them. | tasks | interaction |
- 3.3/6 | RESTART Option | A start-over action clears the sequence and returns to its beginning, and asks for confirmation when entries will be lost. | tasks | interaction |
- 3.3/10 | SUSPEND Option | A user can leave part-way through and later resume from the same point with the work preserved. | tasks | interaction | reword: save draft and resume

### 3.4 Context Definition

- 3.4/1 | Defining Context for Users | Across the steps of a task, keep showing the earlier results that affect the present step and the options now open. | tasks | judgement |
- 3.4/2 | Context Established by Prior Entries | Interpret each action in light of what the user already entered; do not ask for it again. | tasks | interaction | exception: show the interpretation for confirmation if destructive
- 3.4/6 | Highlighting Selected Data | The item an operation will apply to is highlighted. | feedback | interaction |

### 3.5 Error Management

- 3.5/7 | User Confirmation of Destructive Entries | An action that changes a lot, and especially one that is hard to reverse, is announced and must be confirmed before it runs. | feedback | interaction |
- 3.5/8 | User Warned of Potential Data Loss | The confirmation prompt states plainly what data may be lost. | copy | judgement |
- 3.5/10 | UNDO to Reverse Control Actions | Any user action can be reversed straight away with undo. | feedback | interaction |
- 3.5/11 | Preventing Data Loss at LOG-OFF | On sign-out, check for unfinished work and ask for confirmation if anything would be lost. | feedback | interaction | reword: also leaving a page with unsaved changes
- 3.5/12 | Immediate Data Correction | When errors are found after submission, the user can correct them directly and at once. | forms | interaction |
- 3.5/13 | Flexible BACKUP for Error Correction | Users can easily go back to earlier steps to fix a mistake or change their mind. | navigation | interaction |

## 4 User Guidance

### 4.0 General

- 4.0/2 | Explicit User Actions | The system does only what the user asked and takes no additional actions the user might not notice. | actions | judgement | exception: automatic cross-file updating
- 4.0/10 | Clear Control Labels | Every control is labelled clearly with its function. | actions | script |
- 4.0/11 | Clear Data Labels | Every piece of displayed data is clearly labelled. | data | script |
- 4.0/24 | Flexible User Guidance | Guidance that would slow experienced users can be bypassed. | tasks | interaction |

### 4.1 Status Information

- 4.1/1 | Indicating Status | Some indication of system status is available to the user at all times. | states | judgement |
- 4.1/9 | Date and Time Signals | Where the freshness of information matters, show when it was last updated. | data | script |

### 4.2 Routine Feedback

- 4.2/1 | Consistent Feedback | Every input produces a perceptible response, and the screen is never left blank. | states | interaction | reword: no blank page during load or for empty results
- 4.2/3 | Feedback for Control Entries | Whenever the full response will be delayed, show the transaction's status in the meantime. | states | interaction | reword: loading or progress indicator
- 4.2/4 | Indicating Completion of Processing | After a delay, tell the user processing has finished and what they can do next. | feedback | interaction |
- 4.2/11 | Feedback for User Interrupt | After a user interrupts processing, confirm that the system is back in its earlier state. | feedback | interaction |

### 4.3 Error Feedback

- 4.3/1 | Informative Error Messages | An error message says what is wrong and what the user can do about it. | feedback | judgement |
- 4.3/2 | Specific Error Messages | Error messages are as specific as they can be. | copy | judgement |
- 4.3/4 | Advisory Error Messages | When an entry must be one of a few alternatives, the error message lists the valid ones. | feedback | interaction |
- 4.3/5 | Brief Error Messages | Error messages are short while still informative. | copy | script |
- 4.3/6 | Neutral Wording for Error Messages | Error messages do not blame the user, speak as if the computer were a person, or joke. | copy | judgement |
- 4.3/8 | Multiple Error Messages | When one submission contains several errors, the user is told there are several. | feedback | interaction |
- 4.3/10 | Non-Disruptive Error Messages | An error message appears only after the user has finished the entry it concerns. | feedback | interaction | reword: no error while the user is still typing
- 4.3/13 | Cursor Placement Following Error | Besides the message, mark where the error is by moving focus to the offending field. | access | interaction |
- 4.3/14 | Displaying Erroneous Entries | The rejected entry stays on screen with its error message until it is corrected. | states | interaction |
- 4.3/15 | User Editing of Entry Errors | After an error the user re-enters only the part that was wrong. | forms | interaction |
- 4.3/16 | Removing Error Messages | An error message disappears once the error has been corrected. | states | interaction |
- 4.3/17 | Cautionary Messages | An entry that passes validation but looks doubtful prompts a request to confirm it. | feedback | interaction |
- 4.3/18 | User Confirmation of Destructive Entries | A potentially destructive entry or command runs only after an explicit confirming action. | feedback | interaction |

### 4.4 Job Aids

- 4.4/5 | Guidance for Sequence Control | At every point in a sequence the user can see how to continue. | tasks | judgement |
- 4.4/11 | Concise Wording of Prompts | Prompts are concise, with no extraneous words. | copy | judgement |
- 4.4/14 | Maintaining Context for Data Entry | During extended entry, earlier inputs relevant to the current one remain on view. | tasks | script |
- 4.4/23 | HELP | Beyond labels and prompts, further guidance is available on request. | navigation | interaction |

## 6 Data Protection

### 6.0 General

- 6.0/3 | Protection from Computer Failure | The system takes automatic measures to limit data loss when something fails. | states | interaction | reword: autosave, preserved input after a failed request
- 6.0/5 | Protection from Interrupts | An action that would interrupt work in progress must not lose data; if loss is unavoidable, warn and require confirmation first. | feedback | interaction |
- 6.0/8 | Appropriate Ease or Difficulty of User Actions | Frequent or urgent actions are easy, and potentially destructive ones are made hard enough to demand attention. | actions | judgement |
- 6.0/11 | Disabling Unneeded Controls | Controls not needed for the current step, destructive ones above all, are disabled. | actions | script |
- 6.0/13 | Safe Defaults | Any default action or value must be one that cannot cause data loss. | actions | script | reword: default focus and Enter in a dialog go to the safe choice
- 6.0/18 | User Confirmation of Destructive Actions | A potentially destructive action requires an explicit extra confirming step before it executes. | feedback | interaction |
- 6.0/20 | Separate CONFIRM Action | Confirmation is a second, separate action taken in response to a prompt, so it cannot merge with the original request. | feedback | interaction |
- 6.0/21 | Reversible Control Actions (UNDO) | The user can undo the immediately preceding action if it caused unintended loss. | feedback | interaction |

### 6.2 Data Access

- 6.2/4 | Indicating Read-Only Displays | When the user is not permitted to change displayed data, the screen says it is read-only. | states | script |

### 6.3 Data Entry/Change

- 6.3/13 | Data Verification by User Review | When earlier entries need verifying, show them for the user to check and confirm instead of making them type the data again. | forms | interaction |
- 6.3/16 | Displaying Data to be Changed | For a change or deletion of something not on screen, offer to show old and new values so the user can confirm or back out. | feedback | interaction |
- 6.3/18 | Cross Validation of Related Data | Related entries are checked against one another for logical consistency. | forms | interaction |

## Dated, not carried forward

Ten examples of guidelines excluded because they only make sense on character terminals or period hardware. Format: number | title | why excluded.

- 1.1/14 | Cursor Control at Keyboard | Concerns placing a cursor-control device on the physical keyboard.
- 1.1/20 | Consistent HOME Position | Assumes a text cursor with a fixed home cell on each screen.
- 1.4/7 | Protected Labels | Assumes labels are characters on an editable screen that the cursor could type over.
- 1.4/9 | Standard Symbol for Prompting Entry | Assumes a reserved prompt character marking where to type.
- 2.5/11 | Command Entry, Prompts, Messages at Bottom | Reserves the bottom screen lines for a command line and messages.
- 2.6/24 | Brightness Inversion | Reverse video as a highlighting code on monochrome terminals.
- 2.6/37 | Optimal Blink Rate | Specifies blink frequency for blink-coded characters.
- 2.7.1/2 | Display Identification Labels | Short screen codes users type to request a display.
- 3.1.3/4 | Menu Selection by Pointing | Framed around lightpens and touch displays versus keyed option codes.
- 3.1.4/4 | Distinctive Labeling of Function Keys | Concerns labels on dedicated physical function keys.
